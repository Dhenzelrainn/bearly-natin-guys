# Bearly Backend Integration Contract

This file is the shared contract for backend, UI, and database work. The executable source of truth is `database/migrations`; `BEARLY_DATABASE_SCHEMA.md` contains the generated column-level reference.

## Non-negotiable conventions

- Model names are singular StudlyCase; tables are plural snake_case.
- Foreign keys use `<model>_id`. Do not introduce aliases such as `shop_id`; use `store_id`.
- Store money as integer centavos. Never use float/double for totals.
- Persist machine-readable lowercase snake_case statuses; convert them to display labels in presenters/views.
- Every state change with operational significance must be transaction-safe. Shipment movement also creates a `shipment_events` row.
- Controllers validate HTTP input and authorize access; services own multi-table business workflows.
- Reports and dashboard totals are queries over transactional tables. Do not create snapshot/report tables unless a measured performance need appears.
- Files are stored through Laravel disks; database rows contain disk/path, MIME type, size, and document purpose—not binary file contents. Optional Buyer, Seller, Logistics, and Rider registration profile photos accept JPEG/JPG, PNG, or WebP up to 10 MB and use the public `profile-photos` disk prefix. Government IDs and other registration documents use the private local disk and must only be served through role-authorized controllers.

## Temporary form drafts

- `registration_drafts` is keyed by a SHA-256 hash of an HttpOnly browser capability and registration flow. Its encrypted payload contains only allow-listed registration fields and the current wizard step. Passwords, OTPs, consent choices, and registration documents are excluded.
- A successful registration removes its browser-and-flow draft. Draft saves are rejected and stale drafts removed when their normalized email already belongs to an account, preventing delayed page-unload autosaves from recreating completed forms.
- Web OTP codes and verification proofs remain server-side. A short-lived HMAC-keyed cache proof binds the normalized email to the HttpOnly registration-browser capability so the same browser can resume valid verification; final registration still validates proof server-side.
- `seller_product_drafts` is unique per `store_id`; its encrypted payload contains Seller Add Product fields, variants, and color assignments while active. After a successful Product save with failed temporary-file deletion, it may contain only a cleanup marker and retry IDs; it is not a Product record and must not affect inventory or catalog visibility.
- `seller_product_draft_images` stores private temporary image metadata and Laravel disk paths. Image files are queued for cleanup when an image is replaced/removed, when the Seller successfully saves a Product, or when the seven-day inactivity window expires. Metadata is retained when storage deletion fails so cleanup can be retried.
- Registration and Seller product drafts refresh `expires_at` on page use/autosave. The scheduled `drafts:prune-expired` command runs daily, retries pending Seller image cleanup on active and expired drafts, removes expired rows and cleanup-only rows when deletion succeeds, and scans only the private `seller-product-drafts` prefix for unreferenced files older than the configured grace period. Listing/deletion failures are logged and retried without discarding retry metadata or deleting referenced/new files.

## Browser remembered-account sign-in

- Web password and Google sign-in may opt a successful active account into a browser-local Recent Accounts chooser. `remembered_accounts` stores the `user_id`, one-way hash of a random credential, expiry, and last-use time; the raw credential is held only in Laravel's encrypted, `HttpOnly`, `SameSite=Lax` cookie (Secure on HTTPS). Never store passwords, Laravel session IDs, or remembered credentials in JavaScript storage or audit logs.
- A chooser submission must match both the selected account and its valid server-side credential, require an active non-deleted user, rotate the credential under a row lock, regenerate the Laravel session ID, and record a normal authentication audit. The credential expires after 30 days and stale rows are pruned daily. This web feature does not change mobile Sanctum login.
- Remember me is explicit consent that this browser can one-tap sign in to the saved account, including after web logout. Warn against shared devices and allow removing one saved account or clearing all; password changes, account deactivation, and account deletion revoke that user's remembered credentials.

## Registration identity integrity

- Buyer, Seller, Rider, and Logistics registration address selectors use the canonical `Region → Province → City/Municipality → Barangay` order. `/api/psgc/regions` and `/api/psgc/regions/{regionCode}/provinces` provide the Region-level cascade while the existing Province/City/Barangay endpoints remain in use. Submitted labels and codes are untrusted; `PsgcAddressService` canonicalizes the Region from the verified PSGC city code and rejects Region/city mismatches before persistence.
- New registration writes persist the canonical Region name/code to the transitional `users.region`/`users.region_code` fields and the normalized registration address to `addresses.region`/`addresses.psgc_region_code`. The additive `2026_11_02_000003_add_region_to_registration_addresses` migration keeps all four fields nullable so legacy users and addresses remain readable; new registration flows must still submit a valid canonical Region through server-side normalization.
- New Buyer registration requires verified email proof (OTP or a verified Google email on web). In one transaction, create the active Buyer, default delivery address, and Buyer `role_user` assignment. New Buyer registration does not create an `account_applications` / `application_documents` review record, require a government ID, or notify Admins. Web and mobile Buyers may optionally upload a JPG/JPEG, PNG, or PDF Valid ID up to 5 MB to the private local disk in `users.valid_id_path`; Admins may view it through the protected Buyer ID-upload screen, but it does not create an approval queue or affect activation. Optional profile photos use `users.profile_photo_path` and accept JPEG/JPG, PNG, or WebP up to 10 MB. Leave `users.approved_by` and `approved_at` null; do not imply a manual decision. `phone_verified_at` remains null unless the separate phone-verification flow succeeds. Previously submitted pending Buyer applications remain unchanged, are excluded from active Admin queues, and are not automatically converted or deleted.
- Seller, Logistics, and Rider registrations continue through their existing role-specific document and approval workflows. Their accounts remain unavailable until the required reviewing role approves them.
- A Courier is a Logistics-verified work type on the existing Rider role, never a separate/global account role. `account_applications.requested_work_type` is an applicant request only. The sponsoring active Logistics provider must approve the Rider, verify the vehicle documents and vehicle type, and enter the line-haul parcel capacity before a Courier profile is activated. Legacy `rider_profiles.work_type IS NULL` remains compatible with local Rider work and does not grant Courier access.
- Approved Rider account status (`active`, `suspended`, `deactivated`) is managed only by the owning active Logistics provider, derived from the authenticated provider's `logistics_profile_id`; submitted provider IDs are not authorization. Admin may view Rider status but the Admin status endpoint rejects Rider mutations. A status change requires a reason, locks the User/Rider/operational rows, forces `rider_profiles.availability_status` to `offline`, and records actor, old/new status, reason, and affected assignment/job IDs in `audit_logs`. A pending or unapproved Rider cannot be activated through this workflow.
- Suspending or deactivating a Rider cancels only unpicked local pickup assignments (`assigned`, `accepted`, `arrived`) by retaining the assignment row/Rider ID, returning the pickup request to `verified`, restoring `pickup_assigned` shipments to `ready_for_pickup`, and appending a `shipment_events` row. No replacement Rider is assigned automatically. Picked-up assignments remain attached for Logistics intake; active dispatch batches, refund-cash payouts, and Courier line-haul runs remain attached and are not silently reassigned or transferred because their custody semantics require their existing workflow.
- Logistics may explicitly replace an active local pickup assignment only while its status is `assigned`, `accepted`, or `arrived` and every linked parcel remains `created` or `ready_for_pickup`. Require a replacement reason and a different approved, active, available, pickup-capable Local Rider from the same provider with no schedule conflict. Lock and revalidate the provider, assignment, pickup, Rider, parcels, and shipments in one transaction; retain the old assignment as `cancelled`, append a new assignment row, keep the pickup scheduled and shipment status `pickup_assigned`, record actor/reason/old/new assignment references in audit and shipment-event history, and notify the old/new Riders and Seller (or Buyer for a return pickup) after commit. Do not offer or permit replacement after any parcel has been picked up.
- Local approved Riders may share foreground browser GPS only while their authenticated profile is `active` and `available`. `rider_locations` stores only the latest latitude, longitude, accuracy, and server `last_seen_at`; it is cleared when the Rider goes Off duty or is suspended/deactivated. A location older than three minutes or with missing/greater-than-100-meter reported accuracy is not usable for proximity recommendations. Logistics may read it only through provider-owned Rider queries; no cross-provider location response is allowed. Browser background/locked-device tracking is not guaranteed, and Courier line-haul does not use this local pickup recommendation channel.
- Buyer live tracking may read approximate location only for the authenticated Buyer’s own outbound shipment, only while the shipment status is `out_for_delivery`, and only from an active dispatched batch containing that shipment’s `out_for_delivery` parcel(s) assigned to an active, approved, available, local Rider in the shipment’s Logistics provider. Reuse the latest-only `rider_locations` row and the 180-second / 100-meter gates; return no coordinates for stale, invalid, low-accuracy, unassigned, off-duty, Courier, delivered, cancelled, or otherwise ineligible locations. Round coordinates to three decimal places, do not expose Rider identity or location history, and send no-store response headers. Buyer-side polling is foreground-only and must clear the map when the shipment leaves `out_for_delivery`; no map or live location is shown after delivery. No GPS history is persisted.
- The Logistics pickup live map may expose only fresh provider-owned local-Rider GPS reports through the authenticated owning Logistics endpoint; coordinates are returned for map markers or distance only when reported accuracy is at most 100 meters. It must not expose stale locations or history, and marker refresh/selection never creates or changes a pickup assignment; the existing manual confirmation/replacement form remains authoritative. A Rider whose current Sorting Zone covers the pickup address is the primary recommendation tier even when another Rider has closer GPS. Fresh usable GPS distance ranks candidates within each tier and ranks other eligible Riders as fallback when no available conflict-free service-area Rider exists; without usable GPS, service-area match then workload ranks the candidates. Proximity is advisory only; Logistics manually confirms every initial assignment or replacement. Map tiles use the configured Leaflet/OpenStreetMap-compatible source and must retain attribution.
- Active Logistics operators may explicitly share foreground device GPS through `logistics_locations`, which stores only the latest provider-owned coordinate, reported accuracy, and server `last_seen_at`; Stop sharing deletes the row. The location is stale after 180 seconds, and only the authenticated owning provider may read it on internal Logistics maps. Coarse/unknown-accuracy readings may be shown only as explicitly approximate with their reported uncertainty; they are never used for distance ranking, routing, facility-address updates, or automatic assignment. The live marker is distinct from the fixed active Sorting Center `addresses` pin. Do not expose Logistics operator-device GPS to Buyer, Seller, Rider, Admin, or another provider maps; Buyer tracking keeps its custody-based static Sorting Center pin and existing assigned-Rider live-location rules. Background/locked-device tracking is not guaranteed; no location history is persisted.
- Rider vehicle/work-type edits are staged in `rider_vehicle_change_requests`; they do not update the active profile until the owning active Logistics provider approves. Courier activation also requires Logistics-verified capacity and vehicle suitability. Applicant-submitted capacity or verifier IDs are never authoritative.
- Local dispatch capacity is authoritative in `rider_profiles.parcel_capacity` and may be changed only by the owning active Logistics provider through a provider-scoped management action. Capacity changes are audit-logged, cannot be set below the Rider's current active dispatch load, and Rider-submitted capacity is never authoritative. Courier line-haul capacity remains the separate Logistics-verified `linehaul_parcel_capacity` workflow.
- Valid account phone numbers are normalized to E.164 and dual-written to the transitional `users.phone` and `users.contact_number` columns. Both columns have unique database indexes; application validation checks both and provides the user-facing validation message. Null values remain allowed for accounts that do not have a phone on file. Unparseable legacy strings are preserved unchanged rather than silently rewriting account data; they are constrained only by their stored value and must not be treated as verified phone numbers.
- Rider plates are stored uppercase with surrounding whitespace removed and kept in sync between `users.plate_number` and `rider_profiles.plate_number`. Database unique indexes cover each storage location, including soft-deleted rows. Plate punctuation is retained; values that differ only by punctuation are not treated as equal.
- These unique indexes apply across roles for phone numbers and among Rider users/profiles for plates. Soft deletion does not release a phone number or plate for reuse.
- Additive identity migrations preflight existing values. They stop with affected user IDs if aliases disagree or valid phone/plate identities collide after normalization; they do not delete accounts or silently choose a winning record. Unparseable legacy phone values remain unchanged.

### Product variant images

- A variation-specific image belongs to its exact `product_variants.id` through `product_images.variant_id` and uses purpose `variant_sku`.
- A Seller-managed shared color image uses purpose `variant_color`, is attached to one representative `product_variants.id`, and applies to active variants with the same normalized Color/Colour option value.
- Existing image rows with purpose `variant` are legacy color-level images; keep them as a same-color fallback until a Seller replaces or removes them.
- Buyer variation selection prefers a shared `variant_color` image, then its exact SKU image, then a legacy same-color image, then the product's main image (primary when present). This ensures the selected color-gallery image is used consistently for every matching SKU.
- `order_items` snapshots the selected product image's disk and path at checkout so later catalog edits do not change order presentation. Retain an image file while either a catalog image or an order-item snapshot references its disk/path; older rows without a snapshot may resolve through their current product/variant relationships.
- `order_items` also snapshots the purchase-time marketplace category (`category_id_snapshot`, nullable FK to `categories` with delete SET NULL, and `category_name_snapshot`). Admin sales-by-category reporting groups by this snapshot and never substitutes the Product's current category. Legacy rows without a snapshot report as "Category not recorded"; deleting a category clears the id reference while the name snapshot remains readable.

## Seller pricing and campaigns

- Seller Product Discounts and Store Vouchers are `store_promotions` with types
  `product_discount` and `store_voucher`. Store Voucher and minimum-spend amounts
  use integer centavos. Promotion schedules combine `starts_on`/`ends_on` with
  `starts_time`/`ends_time` in the `Asia/Manila` timezone. Existing date-only
  records default to midnight starts and 11:59:59 PM ends; newly selected end
  times include the selected minute. New voucher creation accepts
  `store_voucher` only; existing `product_discount` rows remain readable.
- Store Voucher names may be generated from their offer when the Seller leaves
  the optional internal label blank. Product Discounts retain a Seller-only
  internal name and may carry a separate optional `buyer_campaign_name`; show
  that label only while the corresponding Product Discount is active. Buyer
  pricing and checkout must continue to resolve from the authoritative promotion
  window, not from display metadata.
- Product Discounts are Seller-funded scheduled pricing offers. An active
  Product Discount replaces (does not stack with) the regular Seller discount.
  Reject overlapping scheduled/active Product Discounts for the same Store
  product/SKU. Store Vouchers remain checkout discounts and use the existing
  claim, redemption, cancellation, and refund restoration workflow.
- Bearly Campaign events reuse `platform_promotions`; do not create a parallel
  campaign engine. Campaign-specific event fields are additive. Seller opt-ins
  live in `platform_campaign_participations` and selected product/SKU pricing,
  stock, and per-Buyer limits live in `platform_campaign_participation_items`.
- Campaign events use `draft`, `open`, `active`, `paused`, and `ended`; Seller
  participations use `pending_review`, `approved`, `rejected`, and `withdrawn`.
  Join, review, status, and price-affecting checkout operations are transactional
  and lock the campaign/participation/item rows in a consistent order.
- New campaigns require an Admin-configured `minimum_discount_percent` from 1
  through 90. The nullable column is reserved for legacy campaigns without a
  configured minimum. Seller submissions provide a whole discount percentage
  per product; the server resolves the effective pre-campaign Seller price for
  every eligible active SKU, computes the campaign price in integer centavos,
  and snapshots the baseline, percentage, and computed price. Admin may add or
  raise a minimum on an existing campaign only when every pending/approved
  participation item already meets it; existing submitted prices are never
  rewritten. Admin activation remains required before Buyer pricing is live.
  At checkout, a configured minimum is rechecked against the current effective
  Seller price; campaign pricing is skipped if a Seller price change makes the
  discount fall below the minimum. For Bearly-funded campaigns, pricing is also
  skipped if the effective Seller price has risen above the submitted baseline,
  preventing an unapproved subsidy increase. Legacy campaigns without a
  configured minimum retain their existing behavior.
- Campaign funding is exactly `seller` or `platform`; shared funding is not
  supported. New Admin-created Bearly campaigns are `platform`-funded and
  require a positive `budget_minor`; Admin cannot create uncapped or
  Seller-funded campaign events. Existing uncapped/Seller-funded campaign rows
  remain readable, and legacy Seller-funded rows remain editable without
  changing their funding or Seller-proceeds behavior. Seller-managed Product
  Discounts and Store Vouchers remain independent Seller promotions. Campaign
  funding is immutable after creation. Seller-funded campaign prices reduce
  Seller proceeds. A
  platform-funded price difference is recorded in separate
  `campaign_platform_discount_minor` snapshots on Orders, Seller Orders, and
  Order Items and does not reduce the Seller earnings/commission basis.
- Campaign pricing does not stack: use the best eligible effective price. The
  campaign price is already reflected in the Buyer item price/subtotal; do not
  subtract the same campaign difference a second time from checkout totals.
  Buyer campaign pricing requires an approved participation and an active,
  public campaign within its configured schedule.
  Revalidate campaign dates, approval, stock limits, per-Buyer limits, and
  Bearly budget under checkout locks. Order Item prices and discounts remain
  immutable snapshots if campaign terms later change.
- Campaign banners are stored on Laravel disks; database rows store disk/path
  metadata, not file contents.

### Local Rider delivery verification

- Before Local Rider delivery completion, persist each exact, case-sensitive Parcel barcode scan immediately as a Parcel-scoped `parcel_barcode_verified` `shipment_events` row, scoped in metadata to the current dispatched batch and Rider. Repeated scans are idempotent. Verification appends history but leaves Parcel and Shipment statuses `out_for_delivery`; it never completes delivery. The authenticated Rider may read saved progress across devices, and owning Logistics sees each scan in Dispatch monitoring. Send one after-commit Logistics notification when all Parcels assigned to that Rider's shipment stop have saved verification events. During completion, revalidate persisted verification events against the locked current assignment and Parcel rows; never trust client-submitted barcode lists. Keep explicit recipient, private proof-photo, and exact COD requirements.

### Courier line-haul custody

- Local dispatch, pickup, delivery, and refund-cash Rider assignments accept only local Riders (`work_type = local`) or legacy-local Riders (`work_type IS NULL`). A Courier remains on the Rider role but cannot take local work while Courier is active.
- A Logistics provider creates a provider-scoped manifest for shipments at its own single active Sorting Center. Every shipment must be cross-city, destination-resolvable, and assigned to the same destination provider. The Courier must be active, available, approved, sponsored by that provider, have current Logistics vehicle verification, and have a positive verified parcel capacity. Manifest pieces cannot exceed that capacity; one shipment can be assigned to only one run.
- Assignment and loading do not move parcels or transfer custody. Only Courier departure creates the `shipment_transfers` rows, marks shipment status `handoff_pending`, moves parcels to `in_transit`, and appends `shipment_events` and a line-haul run event in the same transaction. Run arrival is not destination acceptance and does not change the shipment custodian.
- The destination Logistics provider separately accepts each shipment through its existing waybill/parcel intake. Acceptance checks the arrived run and destination ownership, changes `shipments.logistics_profile_id`, receives parcels at the destination's active Sorting Center, and appends shipment events. The line-haul run completes only after every manifest shipment is accepted. Exceptions and resolutions retain actor/reason in `linehaul_run_events`; departed shipments are not reassigned.
- Courier pay is ₱81.25 (8,125 centavos) per server-recorded QR-attendance hour, rounded to the nearest centavo from elapsed seconds and capped at ₱650 (65,000 centavos) / 28,800 paid seconds per Asia/Manila work date. One `courier_daily` row remains the ledger record for each Rider/type/work date and snapshots paid seconds, hourly rate, daily cap, qualifying shift, and run. Multiple fully QR-proven closed shifts are aggregated by the PHT date of check-in. A payout is blocked while any same-date shift remains open; once the day's earning is batched or paid, another shift cannot be opened for that date. Historical fixed-rate rows with null hourly snapshots retain their original amount and existing payout rule.
- Courier run eligibility is unchanged: at least one run assigned to the Courier during one of that work date's closed shifts must reach `completed` after destination Logistics accepts every manifest shipment. QR attendance alone, assignment, arrival, or partial destination acceptance creates no earning. If full acceptance happens after check-out, the earning remains attributed to the shift's PHT work date. Reconciliation on check-out and run completion is idempotent; the unique Rider/type/work-date constraint remains the duplicate guard. Logistics records actual external payout through the existing reviewed Rider payout batch; this is not a wallet or automatic transfer. Couriers remain excluded from local work and GPS.
- Both Couriers and Local Riders must scan the current QR issued by their active owning Logistics provider for check-in and again for check-out. The challenge expires quickly, rotates when refreshed, is provider-scoped, and is stored only as a SHA-256 hash. Scan rows record the provider, Rider, shift, challenge generation, transition, and server time; they never store the raw challenge. Each Rider may redeem one generation once. A live QR may still be shared; this is not a geofence or proof against collusion. Local Rider per-pickup/per-delivery earnings stay unchanged and are not attendance-gated.
- `rider_shifts.checked_in_at` and `checked_out_at` are UTC instants under the app's UTC timezone and are set only by server-side processing of validated QR scans. Convert them to `Asia/Manila` when rendering Rider/Courier and owning Logistics attendance, and label displayed times as PHT (UTC+8). Keep the persisted instants and global app timezone unchanged; Courier work-date attribution also uses `Asia/Manila`.
- The owning Logistics Rider Attendance page roster includes that provider's active-user, approved Local Riders (including legacy null `work_type`) and Couriers for the current PHT date. The dashboard may display the provider-scoped rotating QR; attendance records stay on the dedicated page. A manual absence may be recorded from 11:59 PM PHT only if no same-PHT-date shift check-in exists. `rider_attendance_absences` keeps one immutable provider/Rider/work-date row with the marking user and UTC action time; a later check-in never deletes or replaces it and is displayed separately as late. Absence marking and QR check-in serialize on the Rider profile row.

## Service contracts

### Product compliance

Input: persisted `Product`, scan trigger (`create`, `update`, `manual`, `report`), and an optional authenticated actor for recheck audit history.

Output: `ProductComplianceCheck` with zero or more matches and violations. Active rules scan product names/descriptions; category matching uses configured term rules, not image recognition or an inferred category model. Critical prohibited rules block/hide the product; high-severity rules hold it for review. Actionable automated violations and active in-app `seller_warnings` are deduplicated per product/rule. A later clean scan resolves automated violations/warnings and records a `violation_actions` history entry; an unchanged Admin-dismissed false positive is not reopened. Flagged/blocked products are not buyer-visible. Admin decisions require a reason and append `violation_actions` transactionally. Supported decisions are `dismiss`, `confirm`, `request_correction`, `remove_product`, and `warn_seller`; removal blocks the listing without deleting its product record, and dismissal preserves false-positive history. A final decision cannot be applied twice to the same violation. Seller account suspension/escalation is a separate workflow and is not implied by product moderation.

### Advisory product-image/category consistency

- `product_image_category_checks` is separate from text compliance checks, matches, violations, and Seller warnings. It stores image SHA-256 and listing/category snapshots plus provider/model/prompt version and short validated output; it never stores image bytes or raw API payloads.
- The asynchronous primary-image check runs only after the Seller product-save transaction commits. It is disabled by default and must remain disabled until the Project Owner accepts the applicable Gemini data-use terms. Provider failure is `unavailable`, never `match`; stale image/listing results are not current.
- `match`, `possible_mismatch`, and `uncertain` are advisory observations only. They never block/hide products, change product or compliance status, create violations, or issue Seller warnings. Admin remains solely responsible for any audited manual category-review action.

### Checkout

Input: buyer, Buyer-owned persisted cart items, selected address, COD payment method, and a request key. Output: one `Order`, one `SellerOrder` per store, immutable `OrderItem` snapshots, and a pending `Payment`. Creation must be one database transaction and idempotent using a request key. Placement must reserve stock without reducing `stock_on_hand`; eligible cancellation releases the reservation and appends an `inventory_movements` record.

- For new orders, snapshot `addresses.latitude` and `longitude` together only when both form a valid WGS84 coordinate pair. Keep both `orders.delivery_latitude` and `delivery_longitude` nullable; do not infer a pin from address text or backfill historical orders. Include the pair in the integrity-protected quote context so a changed pin requires a refreshed quote. Do not expose the saved coordinates in Buyer/Seller payloads or general Order serialization.

### Seller Order workflow

- Seller-controlled transitions are `pending → accepted → packing → ready_for_pickup`. The packing checklist is a UI milestone within `packing`, not a persisted `packed` status.
- Every transition appends a `seller_order_status_histories` record with the previous/next status, actor, occurrence time, and reason. The authenticated Seller must own the Seller Order's Store.
- Seller cancellation is allowed only while that Seller Order is `pending`, requires a reason, and atomically releases its reservations with inventory movement history. For a multi-Store COD order, recompute marketplace totals and pending payment amount from the remaining non-cancelled Seller Orders; cancel the marketplace Order/payment only when none remain.
- Lock the marketplace `Order` and its `SellerOrder` rows during transitions; lock affected variants when releasing reservations. Waybills, pickup scheduling, and logistics handoff are separate workflows and must not be implied by `ready_for_pickup`.
- Buyer receipt confirmation moves every non-cancelled Seller Order of a fully delivered marketplace Order to `completed` with a buyer-attributed history record and marks the marketplace Order `fulfilled`. Buyer confirmation is not COD collection evidence and must not mark a COD payment paid. A COD payment becomes `paid` only after Finance reconciles exact cash for every required Seller Order allocation and the aggregate allocations reconcile to the marketplace Payment. Admin payment confirmation must not bypass this rule. Confirmation is idempotent and never completes a cancelled order. `delivered` without Buyer confirmation must not be presented as `completed`.

### Multi-Seller Order outbound packing

- A Seller may combine separately checked-out Seller Orders only when every selected order belongs to the authenticated Store and same Buyer, has the same immutable delivery-address snapshot and compatible outbound Logistics/payment/shipping snapshots, is `accepted`, and has no outbound Shipment. A selected sibling must contain only variants of a Product already in the base Seller Order; cross-Product consolidation is not supported.
- Revalidate selected membership, eligibility, and exact ordered-item quantities on the server while locking all participating marketplace Orders and Seller Orders in deterministic order. Build Parcel contents only from those locked `order_items`; never trust submitted Seller, Store, Product, or item ownership IDs.
- Keep each marketplace Order, Seller Order, order-item purchase snapshot, and Payment distinct. One shared outbound Shipment/Waybill and its Parcel plan may reference multiple Seller Orders through `shipment_seller_orders`. Keep `shipments.seller_order_id` as the legacy/primary Seller Order reference; it is not the complete membership list. Each included Seller Order advances with its own history and notification.
- Preserve each included Seller Order's checkout-time shipping fee, buyer-paid share, platform subsidy, funding source, and zone snapshot. Do not reprice, discount, or automatically refund shipping when combining physical packages. An outbound shipping settlement uses aggregate totals plus one immutable `shipping_settlement_allocations` row per Seller Order; allocation rows must sum exactly to the settlement and its Logistics/Rider shares. Return settlements retain their existing single-return workflow.
- A shared COD collection records the aggregate amount once. `cod_cash_collection_allocations` records the due, collected, and Finance-reconciled amount per included Seller Order and Payment. A marketplace COD Payment is captured only after Finance reconciles the exact aggregate amount due and every active COD Seller Order belonging to that Payment has a matching exact allocation. A Rider/Logistics discrepancy, shortfall, or overage never captures the Payment; do not treat Buyer receipt confirmation as cash evidence.

### COD cash custody, Seller Wallet, and legacy settlements

- Record Rider-reported cash once per outbound COD Shipment in `cod_cash_collections`, including the aggregate amount due, actual amount, signed difference, assigned Rider, owning Logistics provider, and collection time. `cod_cash_collection_allocations` snapshots each participating Seller Order's amount due and its Payment; exact collected and reconciled values are stored per allocation. A mismatch is preserved as `disputed`; it must not capture any affected marketplace payment or qualify Seller proceeds for settlement.
- The cash custody sequence is Rider collection → the same Logistics provider acknowledges the exact Rider-recorded amount → Logistics physically hands off and records the exact cash amount → Admin/Finance physically counts and confirms the exact remitted amount. On acknowledgment, Bearly derives a unique `CODH-` Rider-to-Logistics reference from the collection number. On new Logistics remittances, Bearly derives a distinct `L2F-` Logistics-to-Finance reference from that same unique collection number; existing remittance-reference values are preserved. On new Finance reconciliation, Bearly generates a `BFR-<year>-<collection-id>` internal Finance cash receipt number, stores it in `finance_reference`, and offers a print/save-as-PDF view on Admin Seller Payments. Retrying the same reconciliation is idempotent and must not create a second event or receipt number. Existing Finance references are preserved. The printed Bearly record is not a BIR/tax invoice or bank deposit receipt. Store the three custody references separately (`logistics_reference`, `finance_remittance_reference`, and `finance_reference`). Every state transition appends a `cod_cash_collection_events` row with actor, amount, reference, and occurrence time; receipt views are Admin-only and audited.
- Each positive posted Seller sale transaction not already linked to a legacy `seller_payout_items` row receives one immutable `sale_earning_pending` wallet-ledger entry. For new `zone_based_v1` quotes only, the commission base and Seller sale proceeds exclude the original shipping fee; commission remains at the configured merchandise rate. `SellerOrder.total_minor`, Buyer totals, and COD due retain the full original shipping amount. Existing `flat_per_seller_order` and historical commission/proceeds snapshots are never rewritten. Wallet counters are integer centavos and must reconcile to append-only movement deltas and balance-after snapshots; lock the Seller wallet for every movement. Duplicate posting/release must not create a second credit.
- Pending sale earnings become Available only after the Seller Order is completed, the original payment has `paid_at` and status `paid`, `partially_refunded`, or `refunded`, the three-calendar-day return window has ended, and no return/refund case or refund payout remains open or processing. The release transaction locks the marketplace Order and Seller Order before current reads of case/refund state so a return request cannot race the eligibility check. For COD, every active Seller Order allocation belonging to the Payment must be exact and Finance-reconciled; Finance reconciliation alone never releases earnings. `CODH-`, `L2F-`, and `BFR-` remain distinct cash-custody references and are never used as Seller bank-transfer references.
- Seller recovery rows retain separate `refund_recovery_minor` and `return_shipping_fee_minor` components. Automatic Seller Wallet refund adjustment and the existing withdrawal hold apply only to the refund-proceeds component. A Seller-liable return-shipping fee is recorded as a separate outstanding recovery; it neither blocks nor is automatically deducted from Seller Wallet withdrawals. Admin may record only a verified external collection or an offset already applied to a paid Seller payout.
- Seller refund recoveries remain separate receivables. A closed refund case does not create an automatic wallet offset; recovery is recorded and collected through its separate recovery workflow. Existing `seller_payouts` and `seller_payout_items` remain auditable legacy records; wallet crediting excludes linked transactions. Historical paid payouts are represented in lifetime-withdrawn wallet history without crediting their sale transactions again. Legacy pending batches may only be completed after Finance verifies the external bank transfer; no new Seller payout batches are generated for wallet-ledger earnings.
- Completing a legacy bank-transfer payout requires Finance to record the Seller's `receiving_bank_name` alongside the transfer reference and proof. Store that destination bank name on the payout and in its audit values; never use the field for an account number or COD custody reference.
- Bank account numbers are encrypted at rest and masked to their last four digits in Seller lists. The owning active Seller and authorized Admin/Finance review may access the full number; access is restricted, and full account numbers are never copied into audit values. A withdrawal request stores bank/account snapshots, a Seller-scoped idempotency key, and an atomic reservation of Available funds. It creates status history, audit records, and a Seller notification.
- Finance manually approves/rejects requests, starts processing, records the exact external bank transfer amount/date/reference and optional private proof, then independently verifies success with a note before completion. A reference alone is not proof. Only one transfer record is allowed per withdrawal. Rejection or a Finance-confirmed unsuccessful transfer releases the reservation exactly once; a verified transfer moves it to lifetime-withdrawn exactly once. Bearly does not initiate bank or GCash payouts, hand cash directly, or route Seller payouts through Riders. Proof is stored on a private Laravel disk; Finance may access it during review, while the owning Seller may access it only after verified completion. Every proof access is audited.
- Seller My Earnings and Transaction History are read models of the authenticated Seller's `seller_transactions`, `platform_commissions`, `seller_payouts`, and wallet ledger; all queries are scoped through the authenticated `seller_profile_id`. A legacy payout proof is visible/downloadable by that Seller only after the payout is paid and the private receipt exists; access is audited. Order-item images use the immutable checkout image snapshot where present, with product image fallback; subcategory is display metadata and never changes ledger amounts.

### COD cash refunds

- A refund requires an actually paid COD payment (`paid` or `partially_refunded` with `paid_at`), completed Seller response/Admin responsibility decision, and Seller inspection for physical returns. Unpaid or cancelled orders have no cash refund.
- Finance records an exact cash handoff to the original outbound Logistics provider. Bearly generates a unique `CFH-` handoff reference when Finance confirms the physical handoff; the same reference is retained on the payout, event history, and Logistics workspace. That provider acknowledges receipt and assigns an active, approved Rider belonging to it. Rider receipt, delivery attempt, failure, return of the full amount, Logistics return confirmation, and Buyer receipt verification are distinct audited `refund_cash_payout_events` transitions.
- When Logistics assigns a Rider to a Buyer cash refund, Bearly generates an `ACK-<payout_no>-A<n>` acknowledgment reference, stores it on the payout, and appends it to the assignment event. Logistics prints the Bearly-branded acknowledgment form or saves it as PDF and hands the paper form to the Rider with the cash before dispatch. The Rider confirms the form's reference against the active assignment when acknowledging cash receipt; the event records that reference. The Buyer signs only after receiving the full amount; the Rider uploads the signed proof privately on a Laravel disk. Failed-attempt events retain that attempt's reference, and reassignment after the full cash is returned generates a new reference. Logistics verifies the displayed reference against the signed proof; Admin/Finance completes the refund only after Logistics verification and records a reason. A Rider must never personally fund a refund. Seller liability/recovery remains separate from payout custody and no automatic Seller-payout offset is permitted.

- Reviews store a 1–5 rating, a comment of up to 500 characters, and an optional photo (JPG/PNG/WebP, max 2 MB) on Laravel disks; rows store metadata/path, not binary content.

### Zone-based Buyer shipping and quote snapshots

- New or edited SKUs require packaged weight and L×W×H; weight and each package dimension are stored to three decimal places. Legacy SKUs with null package data cannot be quoted.
- Quote one combined parcel per `SellerOrder` using the deterministic `greedy_minimum_bounding_box_v1` estimate. Billable weight is `ceil(max(actual_weight, parcel_volume / divisor))`, with a one-kilogram minimum; package measurements remain in the quote for delivery planning.
- New checkout quotes price one fee per combined `SellerOrder` shipment, never per product, quantity, or parcel. `zone_based_v1` defaults to a 5000-centavo base plus 500 centavos per zone level: zone 0 same municipality ₱50; zone 1 different municipality/same province ₱55; zone 2 different province/same region ₱60; zone 3 different region/same island group ₱65; zone 4 different island groups ₱70. Billable weight does not change the Buyer fee.
- Zone classification uses the exact persisted 10-digit PSGC city code, the validated PSGC province-parent code when available, the versioned `resources/data/psgc-shipping-zones.json` province/region map, and its region-to-island-group mapping. The snapshot is sourced from PSGC Cloud `/regions` and `/provinces` data; island-group assignment is a versioned Bearly shipping classification. City/province display names are never used as geographic identity. Missing, unknown, mismatched, or same-region locations without a reliable province parent fail validation; no GPS, routing, or name-only fallback is permitted.
- Admin edits the existing shipping settings: `system_settings.shipping.base_fee_minor`, `shipping.zone_surcharge_per_level_minor`, and `shipping.volumetric_divisor`. The initial base falls back to the old `shipping.seller_order_fee_minor` value if present, then to the 5000-centavo default; new Admin saves write the zone settings and leave legacy configuration/history intact. Changes include an audit actor, reason, and before/after values. Marketplace shipping is the sum of independently priced Seller Orders.
- The volumetric divisor defaults to 5000 and changes only the informational billable-weight estimate. Former `shipping_rates` rows remain legacy and do not price new quotes.
- Calculate the original zone fee before eligible vouchers. Preserve original fee, Buyer-paid shipping, platform shipping subsidy, funding source, zone level, base/surcharge, and canonical location inputs on each `SellerOrder` (`shipping_fee_minor`, `buyer_paid_shipping_fee_minor`, `platform_shipping_discount_minor`, `shipping_funding_source`, and `shipping_quote`). A platform shipping voucher is Bearly-funded and does not reduce the Logistics/Rider allocation. Preserve Store Voucher plus platform shipping-voucher stacking and existing eligibility/caps; Buyer-paid fee plus Bearly subsidy must equal the original fee and never be negative.
- The Buyer quote is integrity-protected and expires after ten minutes. At placement, revalidate the cart, address identifiers, item snapshots, package estimate, zone inputs, current fee settings, and voucher allocations against the accepted quote; changed terms require a refreshed quote. Persist the applied provider, pricing rule, quote inputs, and immutable fee snapshot on each `SellerOrder`. Admin setting changes never rewrite confirmed orders.
- `shipping_quote.package_items` is the immutable per-SKU, per-unit package snapshot (quantity, packaged weight, and dimensions); the combined bounding-box estimate remains the checkout shipping-price/planning input and is never repriced from the Seller's final packing choice. Before outbound preparation starts, the Seller submits a packing plan. Default to one physical Parcel per ordered unit, but permit units from one or more order items to be combined or split across packages. Persist each allocation as `parcel_items(parcel_id, order_item_id, quantity)`; lock the Seller Order's order items and require every ordered quantity to be assigned exactly once, with no foreign item IDs or empty parcels. Record each physical package's Seller-confirmed weight and outside dimensions on its Parcel. Keep one outbound `Shipment` and one `Waybill` per Seller Order, and set `waybills.piece_count` equal to the actual Parcel count with contiguous `piece_sequence` values. Print one label per Parcel with the shared Waybill reference, exact recorded contents and package measurements, and the unique `parcels.parcel_no` as the scannable piece barcode. Older quotes without per-SKU `package_items` retain a single aggregate-package default; do not silently rewrite or backfill historical shipments or Parcel contents.

Only an active Admin may approve and publish or return a submission with a reason; approval records the Admin's confirmation that the cited source was reviewed. `pending_approval` and `changes_requested` versions remain private to the appointed manager and Admin, and a pending replacement does not displace the current published version. ### Shipping settlement and Rider payout

- Outbound settlements are unchanged: a delivered, completed `zone_based_v1` Seller Order creates at most one outbound `shipping_settlements` row and one linked Rider earning after the shared Seller Wallet gate passes (payment, completed Seller Order, ended three-calendar-day return window, no open/processing return or refund, and exact Finance reconciliation for every positive-COD outbound shipment). Failed, cancelled, returned, legacy flat-fee, and otherwise undelivered outbound work is not eligible.
- An Admin-approved physical `return_refund` may use `rider_pickup` or `buyer_dropoff`. Buyer drop-off is available only at the active Sorting Center assigned to the immutable Buyer order city; the client cannot select a provider or center. After approval, the Buyer has three calendar days to drop off the waybill. If the deadline is missed before Logistics accepts the parcel, the Buyer may switch to the existing Rider-pickup path and Bearly recalculates/snapshots the reverse route quote. Logistics must scan the exact assigned center before custody is recorded. `refund_only` never creates a reverse shipment, fee, or Rider earning.
- Every physical reverse shipment stores an immutable `return_shipping_quote` and its exact `shipping_fee_minor`. The route begins at the Buyer order address for Rider pickup, or the assigned Buyer-city Sorting Center for drop-off, and ends at the Seller pickup address. Use canonical PSGC city identity and saved item/package snapshots; never accept a client-supplied fee, provider, or center. The Admin's existing `Refund.financially_responsible_party` decision also governs return-shipping cost. The approved full Buyer refund remains unchanged; the fee is not deducted from it.
- A return settlement is eligible only after the approved reverse shipment is successfully delivered to the Seller and its final Rider delivery attempt/event is recorded. It does not wait for Seller inspection/refund completion and does not use the outbound three-day, payment, or COD settlement gate. Failed, cancelled, undelivered, or unreceived drop-off returns create no settlement.
- Split each immutable shipping fee in integer centavos and make the shares sum exactly to the fee. A no-transfer, single-provider outbound delivery remains `floor(fee × 40 / 100)` to its Logistics provider and the remainder to the final Rider (the existing 40/60 allocation). For an outbound shipment with one accepted inter-Logistics transfer matching the immutable origin and final custodian, allocate `floor(fee × 10 / 100)` to origin Logistics (L1), `floor(fee × 30 / 100)` to destination/final-delivery Logistics (L2), and the exact remainder to the final Rider. Any centavo remainder after flooring the two provider shares belongs to the Rider. Bearly shipping subsidy does not change the split. Returns, including transferred returns, retain their existing 40/60 allocation to the current custodian and the Rider whose completion delivered the return to the Seller.
- Logistics may register bank-transfer and GCash payout destinations under its own authenticated profile. Destination numbers are encrypted at rest and masked to their last four digits in Logistics lists and audit data. New destinations remain `pending_review` until active Finance independently verifies them; rejected or deactivated destinations cannot be selected. Finance-only full-detail access is audited. Changed details require a new destination row; prior rows remain available for settlement history.
- Admin/Finance manually remits single-provider outbound and return settlements as one 100% provider transfer, then records the settlement. For inter-hub outbound delivery, Finance records two separate actual transfers: 10% to L1 in `shipping_settlement_origin_remittances` and 90% to L2 in the existing `shipping_settlements` remittance fields. The L2 transfer includes its 30% share plus the final Rider's 60% pool. Each bank/GCash transfer requires a verified, active destination belonging to that specific recipient; the used payout-account link and masked destination snapshot are retained separately for L1 and L2. Neither transfer is initiated by Bearly. Confirmed cash receives a distinct generated `SRM-` reference for each recipient and an Admin-only printable receipt; the receipt is an internal handoff record, not a bank transaction reference or tax invoice. An inter-hub settlement is `partially_remitted` after only one recipient is paid and `remitted` only after both transfers are recorded. The Rider earning remains `pending` until both transfers are complete, then becomes `posted` under the existing L2 payout-batch gate. Finance advances Seller-liable return fees to the current Logistics custodian and records a separate Seller recovery; that return-fee component is not automatically deducted from Seller Wallet. Logistics records the exact Rider-pool payout; digital methods require the actual provider reference, while confirmed physical cash payouts receive a Bearly-generated `LRP-` internal reference and an audited, provider-scoped printable receipt. Eligible pickup earnings are `posted` after successful collection or explicit size-class review. Either Rider earning type becomes `paid` only after Logistics records the actual payout. COD product cash remains exclusively in the Rider → Logistics → Finance `cod_cash_collections` workflow.
- Outbound and return Rider earnings share `rider_earnings`; `rider_earning_payouts` is unique per earning and stores exact amount, method, reference, paid date, recording actor, and reason. Logistics can access and pay only its own Riders/records. Retry paths must not duplicate settlements, earnings, remittances, or Rider payouts.
- Local Riders use `rider_profiles.specialization` values `pickup_only`, `delivery_only`, or `both`; existing profiles default to `both`. Only approved, active, available, provider-owned local Riders with matching specialization can be assigned. Courier work remains line-haul only. Manual availability remains `available`/`offline`; operational task state is derived from active assignments and never overwrites the manual choice.
- Pickup requests and delivery dispatches use half-open planned windows for conflict checks (`existing_start < requested_end` and `existing_end > requested_start`), so adjacent windows do not overlap. Delivery dispatch still starts immediately; its planned window is scheduling metadata, not a delayed-dispatch instruction. Legacy active delivery batches without a window conservatively block additional conflicting work until their parcels are final. Assignment paths lock the Rider and reject duplicate/concurrent work server-side.
- Local Rider attendance is report-only: check-in/check-out cannot gate assignments or existing per-job earnings, and a pickup/delivery earning links to the shift containing its event time when one exists. Courier daily compensation is the separate exception: a closed check-in/out shift and a completed assigned line-haul run with full destination acceptance are both required, with no pay for attendance alone.
- A successfully collected outbound Seller parcel earns a separate Logistics-funded pickup earning: default ₱15 (1500 centavos) for recognized regular size classes and ₱30 (3000 centavos) only for the exact saved `size_class = bulky`. Admin settings are `rider.pickup_rate_regular_minor`, `rider.pickup_rate_bulky_minor`, and `rider.pickup_regular_size_classes`; the default regular classes are `small` and `regular`. The earning snapshots the saved class and rate and is unique by pickup assignment plus parcel. Missing/unrecognized classes are held for provider review and excluded from payout until classified; Logistics may classify an outbound parcel during waybill intake, which classifies a matching held earning through the existing audited earning workflow. The parcel class, earning snapshot/rate, and intake event must agree; do not silently reclassify a posted or paid earning. Never infer class from parcel count or dimensions. No Seller charge, pickup quota/rate for returns, or delivery pickup-rate applies.
- Pickup earnings remain distinct from delivery settlement earnings. Delivery amounts and existing settlement/Finance gates are unchanged; an outbound delivery earning cannot enter a payout batch before its shipping settlement is remitted and the earning is posted. Eligible earnings can be consolidated across assignments and shifts for one Rider/provider into a batch with immutable amount/type items. Logistics must review/approve the batch before recording the actual external payment; each earning is then marked paid once and receives its existing unique payout row. The individual-earning endpoint cannot bypass the batch workflow. Digital payment references are actual external references; confirmed cash uses a generated `LRP-` internal reference and a provider-scoped receipt. Batch/payment transitions are transactional, audited, ownership-scoped, and retry-safe.

### Shipment and waybill creation

Input: fulfillable `SellerOrder`, logistics provider, origin/destination snapshots, immutable checkout package details, and a validated Seller packing plan. Output: one `Shipment`, unique `Waybill` number plus unguessable scan token, one `Parcel` row per Seller-declared physical package, exact `parcel_items` quantities, and initial event. Require exact order-item quantity allocation and positive package measurements before creating any fulfillment records. `Waybill.piece_count` must match the Parcel rows and their contiguous piece sequence before printing/marking ready or requesting pickup. Each parcel number is unique and is printed as that piece's barcode; every label retains the shared Waybill reference. A waybill must never be created from arbitrary manually entered buyer/order data.

### Parcel intake scan

Input: authenticated Logistics user, unique `parcels.parcel_no` barcode (or a Waybill reference to open its manifest), Sorting Center, scan method, and the selected parcel's configured `size_class`. Web intake receives one exact Parcel per submission and reports received/total Waybill-piece progress; a Waybill-only web form submission never receives all pieces. Each parcel is classified individually by inspection; never infer size from product contents, imagery, dimensions, weight, or piece count. Existing JSON callers may continue submitting a Waybill identifier to receive the full Waybill for compatibility; when a size map is supplied it must cover exactly every Parcel being received. Output: updated Parcel and its receipt event; shipment-level `at_sorting_center` and pickup/Buyer-dropoff completion occur only after every parcel has a receipt event. A matching held outbound pickup earning is classified/audited in the same intake transaction; posted or paid earning snapshots cannot be silently changed. Lookup is provider-scoped, returns piece progress and recorded contents, and uses the same service.

### Barangay delivery zones

- `sorting_zones.destination_rules` stores `province`, `city_municipality`, `psgc_city_code`, and a `barangays` string list. PSGC city code is authoritative for city identity when present; barangays continue to match by normalized name. Each Logistics profile has exactly one Sorting Center, and each active zone belongs to that Center; active barangay coverage must not overlap across zones in the Center.
- Logistics creates zones from the official province → municipality/city → barangay selector. The account's single Sorting Center is assigned automatically; clients cannot choose a center. Zone codes are generated from the municipality and a per-center sequence; zone names use the municipality and first covered barangay.
- Logistics may edit coverage or archive an owned zone in the Sorting Center UI. Archiving sets `status=inactive` and `deleted_at`; restore clears `deleted_at`, activates the zone, and rechecks for overlapping active coverage. Coverage changes and archiving are rejected while the zone has non-final parcels or an active dispatch batch. Rider center/zone assignments are automatically recalculated after a coverage change, archive, or restore. Archived zone codes remain reserved and are not reused.
- Permanent deletion is available only for archived zones and is blocked while non-final parcels or active dispatch batches still use the zone. It permanently removes the zone row while retaining parcel, dispatch, and shipment-event records; their nullable zone foreign keys are set to `NULL`. In particular, `dispatch_batches.sorting_zone_id` uses `ON DELETE SET NULL` so historical batches survive.
- Parcel sorting matches province, municipality/city, and barangay against the zone coverage (case-, punctuation-, and accent-insensitive). Outbound parcels use the immutable marketplace Order destination snapshot; return parcels use their reverse Shipment destination address. A parcel with no matching active zone cannot be sorted into a zone.
- Dispatch includes only ready parcels whose destination matches the target zone. A parcel assigned to a different or uncovered zone remains undispatched until corrected. Prefer an eligible Rider assigned to the target zone when that Rider has capacity for the whole batch. If none can carry the whole batch, the Logistics board may offer approved, active, available, local, delivery-capable Riders with sufficient remaining capacity from another active zone at the same provider and Sorting Center. Logistics must explicitly select the Rider; this is a one-time overflow assignment and never changes the Rider's home zone.
- The dispatch service locks and revalidates the target zone, Rider, provider, active Sorting Center, Rider's current active zone, specialization, availability, capacity, and planned schedule. It derives `assignment_mode` (`zone_match` or `nearby_zone`) from persisted zone ownership; never trust a client-submitted mode. `nearby_zone` requires a 5–1,000 character Logistics reason. Persist the target zone on `dispatch_batches.sorting_zone_id`, the assigned Rider zone on `rider_zone_id`, mode and reason on the batch, and immutable target/Rider zone ID+code snapshots on parcel/shipment event metadata. The nullable Rider-zone foreign key uses delete SET NULL so an archived zone can still be permanently removed without blocking cleanup; event metadata preserves the historical zone snapshot. Same-zone dispatches need no override reason.
- GPS proximity is optional and advisory. Use an immutable order coordinate snapshot only when every distinct batch destination has a valid pin, and use only provider-scoped local Rider fixes no older than 180 seconds, with valid coordinates and reported accuracy at most 100 m. Distances are approximate averages of straight-line geodesic distances to distinct stops, not road mileage or ETA. Missing/invalid pins, missing/stale/low-accuracy/invalid Rider GPS, or overlapping accuracy ranges suppress any single-Rider “closest” recommendation; show no fabricated distance. No usable GPS does not block a manually approved same-provider/same-center overflow dispatch.

### City-scoped Logistics and Rider assignment

- `logistics_profiles.psgc_city_code` is the authoritative municipality/city for a Logistics account, sourced from its registered Sorting Center/application address and uniquely owned by one profile (including inactive/soft-deleted profiles). Registration and approval must preserve the city; a profile cannot silently move to a different city. Each city has at most one Logistics profile, and each profile has exactly one Sorting Center.
- Sorting Zones are limited to the owning Logistics city and belong to its single Sorting Center. Zone creation uses that center automatically; no center selector or client-supplied `sorting_center_id` is accepted.
- Rider registration must select a Logistics sponsor serving the Rider's registered PSGC city. Approval and later refresh derive `home_sorting_center_id` and `current_zone_id` from the Rider's Home address and matching active barangay coverage. Unmatched Riders remain unassigned and cannot receive dispatch; Logistics cannot manually override the city/barangay match.
- New checkout snapshots the validated delivery `psgc_city_code` onto `orders`; outbound shipment snapshots it to `shipments.destination_city_code`. Return shipments snapshot the Seller pickup address city code. Text address fields remain immutable/display context but do not decide which Logistics profile owns last-mile delivery.

### Inter-Logistics shipment handoff

- `shipments.logistics_profile_id` is the current custodian; `origin_logistics_profile_id` preserves the first provider for audit and historical workflows. Each outbound or reverse shipment can have at most one direct city handoff in `shipment_transfers`.
- The current Logistics custodian may send a shipment only after every parcel is received at one of its active Sorting Centers and before sorting/dispatch. The target is resolved server-side from the immutable destination city code; clients cannot submit a destination provider.
- Sending creates one `shipment_transfers` row in `sent`, changes shipment state to `handoff_pending` and parcels to `in_transit`, and appends one `logistics_handoff_sent` shipment event per parcel. The origin remains current custodian until acceptance and cannot sort or dispatch in-transit parcels.
- The destination Logistics account may preview an incoming transfer using an exact Waybill identifier or the printed Parcel barcode. Parcel lookup resolves to its parent Waybill and previews the full shipment parcel count; it is scoped to the recorded destination and, when a Courier run is assigned, is unavailable until that run is `arrived`. The one active destination Sorting Center is resolved automatically from the authenticated account. Acceptance locks and revalidates the pending transfer, destination city, custodian, parcel states, and center ownership; it atomically changes current custody, records the accepting actor/center/time, returns every parcel in the shipment to `received`, clears prior zone assignment, and appends `logistics_handoff_accepted` events. Event metadata records whether the accepted identifier matched the Waybill or a Parcel barcode. Repeated, foreign, wrong-city, and invalid-state operations must not duplicate events or custody changes.
- Cross-city physical returns enter custody at the Logistics provider serving the Buyer/order city by either Rider pickup or the assigned Sorting Center's scanned Buyer drop-off, then use the same handoff workflow to reach the Seller pickup-address city account before local sorting and delivery. COD collection remains owned only by the Rider and current Logistics custodian who completed outbound delivery; the immutable origin provider is retained separately.

## Authorization invariants

- Buyers access only their carts, orders, payments, returns, disputes, and conversations.
- Sellers access records through their `seller_profile`/`store`; never trust a submitted seller ID.
- Logistics users access shipments whose current `logistics_profile_id` belongs to them; only the recorded destination account may accept a pending handoff. Historical origin-provider data does not grant current custody access.
- Riders access only active assignments tied to their `rider_profile`.
- Admin actions record the acting user and reason in action/event/audit tables.

## Seller conduct, Buyer-data minimization, and fulfillment review

- The `SELLER-CONDUCT-OFF-PLATFORM` platform policy is created as a draft and has no Seller access effect until an Admin publishes an effective version. Seller Center access then requires an append-only `policy_acceptances` record for that exact active `policy_version_id`; a later effective published version requires a new acknowledgment. Persist the accepting user, version, and timestamp and audit the acknowledgment.
- Disputes use `type = order_issue` by default. `off_platform_solicitation` is a separate Buyer report on an owned Seller Order and may coexist with a different active order-issue dispute. Derive the Buyer/Seller participants from the order; do not accept participant IDs from the request. Evidence remains private on the local disk and available only through the existing authenticated, role-scoped evidence routes.
- An off-platform report has no refund amount and can resolve only to `policy_violation_found` or `no_violation_found`. Those findings do not themselves initiate payment, COD, refund, order/shipment status, suspension, or other automatic punishment workflows. Every finding requires an Admin reason and audit/event history.
- Seller Manage Orders, Returns list/detail, and Waybill list rows may show the Buyer account name for the authenticated Store's orders/cases; label it as Buyer because the delivery recipient can differ. Keep Buyer identity generic in tracking and never match Waybill searches by Buyer account/recipient name. Do not expose Buyer phone, email, or full address through Seller pages, payloads, tracking, or search. A Seller may use the recipient name and full delivery address only on the audited Bearly-generated Waybill label needed to prepare the parcel; that label must not expose the Buyer phone. Logistics/Rider delivery workflows retain their authorized delivery-contact access.
- Admin Waybill PDF access is authenticated and audited because the label contains full delivery-address data. A missed scan or expired persisted pickup appointment is an advisory review cue only. It is not proof of Seller misconduct and must not automatically change Seller, order, payment, or shipment standing.

## Returns and refunds

- A Buyer may request a return/refund within three calendar days after the Seller Order's recorded completion time. Requests select immutable order-item quantities; the requested value is calculated from saved item and Seller discount snapshots and cannot exceed the remaining paid order value.
- A case moves `awaiting_seller → under_review` only after the Seller submits a response and supporting evidence. Admin may then reject, request Buyer/Seller evidence, or approve; only Admin decides the claim.
- Admin approval still authorizes physical returns only after the Seller responds. The Buyer-selected Rider pickup or same-city Logistics drop-off is stored on the case; a drop-off waybill is not accepted before approval and must be scanned once by the assigned active Sorting Center. If the three-calendar-day post-approval drop-off deadline expires before intake, the Buyer may switch to Rider pickup; the case remains approved and the reverse fee is recalculated from the Buyer address. Do not select an arbitrary provider or fall back to another provider if the Buyer-city provider is inactive; block approval until the active provider is available.
- The return destination is the Seller pickup-address city; if different, the Buyer-city provider receives the parcel by Rider pickup or Buyer drop-off, then sends it through the audited inter-Logistics handoff to the Seller-city provider for local sorting and delivery. Return parcel scans use provider-scoped pickup/intake/sorting/dispatch/Rider lifecycle and append shipment events; outbound Buyer tracking excludes return-purpose shipments.
- Physical-return refunds remain pending until the Seller records inspection for every returned item. Only items marked sellable and restock are added to stock, with an `inventory_movements` record. Other inspected units are quarantined or disposed, not added to stock.
- Admin approval records a required financial-responsibility party (`seller` or `platform`) and evidence-based reason; this is separate from who sends the money. Admin is always responsible for sending the Buyer refund externally.
- One approved refund is one exact, full payout. Completion requires an explicit Admin confirmation that the external payout was already made, persists the actual payout amount (equal to the approved amount), method/reference/date, and a private receipt or Buyer acknowledgment. Bearly does not initiate a transfer. Completion is transaction-safe, idempotent, and bounded by captured payment.
- For Seller-attributable refunds, completion reverses the proportional platform commission and creates a separate Seller recoverable balance for net proceeds. It is not an automatic deduction from Seller settlements. Platform-attributable refunds create no Seller recovery or commission reversal.
- A Seller recovery may be recorded only after Admin verifies an external collection or an offset already applied to a paid Seller payout. Recovery events retain the actor, amount, date, reference, method, and optional paid-payout link; they do not change a Seller payout or move funds.
- Return evidence is private on the local Laravel disk. Buyer, Store-owning Seller, and Admin downloads require authenticated, role-scoped routes; state changes retain actor, reason, and case event/audit history.
- External payout receipts are private on the local Laravel disk and available only to the owning Buyer and Admin through audited downloads. Seller views show the finalized payout details and any outstanding/recovered balance, but not the Buyer’s receipt file.

## API response baseline

Successful service-backed JSON endpoints return `{ "data": ..., "message": ... }`. Validation uses Laravel's standard `422` errors; unauthenticated is `401`, unauthorized is `403`, missing is `404`, and invalid state transition is `409`. Dates use ISO-8601 and money fields expose integer centavos plus optional formatted display values.
